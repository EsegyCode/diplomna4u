## B3. Дизайн-система

### Як будувати
Взяти значення з розділу A5 і винести **все** у CSS-змінні `:root` в `global.css`. У компонентах — жодних «сирих» hex-кольорів, лише змінні.

### Мінімальний набір токенів
```css
:root {
  /* Кольори (значення — з A5) */
  --color-bg:            ;  /* фон сторінки */
  --color-bg-alt:        ;  /* фон альтернативних секцій */
  --color-surface:       ;  /* фон карток */
  --color-border:        ;  /* межі, розділювачі */
  --color-text:          ;  /* основний текст */
  --color-text-muted:    ;  /* другорядний текст */
  --color-brand:         ;  /* основний бренд-колір */
  --color-brand-dark:    ;  /* hover */
  --color-accent:        ;  /* світлий акцент, іконки */
  --color-cta:           ;  /* CTA-кнопки і липка кнопка */
  --color-cta-dark:      ;  /* hover CTA */
  --color-success:       ;  /* оплата/гарантія/успіх */
  --color-danger:        ;  /* помилки форми */

  /* Типографіка */
  --font-heading: ;
  --font-body:    ;

  /* Форма */
  --radius-card: ;   /* 16–20px за замовчуванням */
  --radius-btn:  ;
  --shadow-card: ;   /* м'яка тінь */
  --container:   1200px;
  --tap-min:     48px;  /* мінімальна висота CTA */
}
```
Якщо в A5 задано лише «настрій» без кольорів — агент сам підбирає палітру, дотримуючись контрасту **WCAG AA (≥ 4.5:1)** для тексту, і виписує її у фінальному звіті.

### Загальні правила
- Mobile-first, **основний брейкпоінт 900px** (`@media (min-width: 900px)`).
- Тач-зони: CTA-кнопки ≥ **48px** висоти; усі інші кнопки й посилання ≥ **44×44px**.
- Багато повітря, закруглення карток, м'які тіні — якщо A5 не каже інакше.
- Іконки — inline SVG (лінійні/outline), без іконкових бібліотек.
- Фото — плейсхолдери, якщо в A5 немає реальних; плейсхолдер позначити `TODO: замінити фото`. Усім `<img>` — `alt`, `width`/`height`, `loading="lazy"` (крім hero).
- Анімації — легкі, поважати `prefers-reduced-motion`.

## B4. Навігація та глобальні елементи

**Header:** логотип/назва → пункти меню з A6 (без dropdown, якщо A6 не вимагає) → акцентна кнопка (виділена `--color-cta`) → телефон `tel:` (desktop, праворуч). На мобільних — бургер-меню з тач-зонами ≥ 44px.

**StickyCallButton** (якщо A7 = ✅), підключається один раз у `BaseLayout.astro`:
- Desktop: `position: fixed; bottom: 16px; right: 16px`.
- Mobile: горизонтальна панель на всю ширину знизу: «Зателефонувати» + номер.
- Колір `--color-cta`, іконка телефону, `href="tel:<номер у форматі E.164>"`.
- Pulse-анімація: scale 1 → 1.05 → 1, 2s, infinite (вимикається при `prefers-reduced-motion`).
- `z-index: 999`; не перекриває форму й футер (додати відступ знизу сторінці на мобільних).

**Footer:** назва, короткий опис, навігація, контакти, графік, соцмережі, копірайт.

## B6. Форма заявки (LeadForm)

- Поля — з A8. Типові: ім'я (text), телефон (tel, маска, формат з A2), опис (textarea), чекбокс згоди на обробку персональних даних (required).
- **Client-side валідація:** непорожні обов'язкові поля, коректний формат телефону, чекбокс обов'язковий. Помилки — під полем, текстом (не лише кольором), `aria-live="polite"`.
- Honeypot-поле проти спаму (приховане, не `display:none` для скрінрідерів — `aria-hidden` + `tabindex="-1"`).
- Блокувати кнопку на час відправки, показувати стан «Відправляємо…».
- Після відправки — повідомлення про успіх або помилку з номером телефону для дзвінка.
- Форма використовується на головній і на окремій сторінці — **один компонент**, без дублювання коду.

### ⚠ Про mock-API при SSG
У статичній збірці файл `src/pages/api/lead.ts` **не обробляє POST-запити** на хостингу. Тому:
1. У `LeadForm` ввести константу `MOCK_MODE = true`. При `true` — імітувати успішну відповідь (`setTimeout`), без реального `fetch`.
2. При `MOCK_MODE = false` — `fetch('/api/lead', { method: 'POST', body })` (або URL з A8).
3. `api/lead.ts` створити як заглушку з коментарем `// TODO: підключити реальний backend / Telegram-бот / CRM / Formspree / serverless-функцію`.
4. У фінальному звіті окремо нагадати, що форма **не надсилає реальних заявок**, поки не підключено backend (спосіб — з A8).

## B11. Модуль: локальні сторінки міст (geo-pages)

> Підключається, **лише якщо в Частині A заповнено розділ A14**. Інакше пропустити.

### Мета
Окрема статична сторінка під кожне місто (`/sumy/`, `/kyiv/` …), щоб ловити регіональні запити. Каркас спільний, але **частина контенту унікальна для міста**. Сторінки, що відрізняються лише назвою міста, — це doorway-спам, який Google знижує в видачі, тому нижче є запобіжники.

### 1. Дані — `src/data/cities.ts`
Єдине джерело правди. Інтерфейс:

```ts
export interface City {
  slug: string;            // латинська транслітерація, kebab-case: "bila-tserkva"
  name: string;            // "Біла Церква"
  inCity: string;          // з прийменником, правильний відмінок: "у Білій Церкві"
  genitive: string;        // "Білої Церкви"
  region: string;          // "Київська область"
  universities: { name: string; short?: string; note?: string }[]; // локальні ВНЗ
  localFacts: string[];    // регіональна специфіка (ґрунти, ліси, екологія тощо)
  localFaq: { q: string; a: string }[]; // питання, унікальні для міста
  intro?: string;          // унікальний вступний абзац міста
  localContentReady: boolean; // true лише коли заповнені universities/localFacts/localFaq
}
export const cities: City[] = [ /* з A14 */ ];
```
Відмінкові форми (`inCity`, `genitive`) **брати тільки з A14**, ніколи не утворювати програмно.

### 2. Роутинг (SSG)
- `src/pages/[city]/index.astro` з `getStaticPaths()` по `cities`; хаб — `src/pages/mista/index.astro`.
- В `astro.config.mjs`: `trailingSlash: 'always'`, `build: { format: 'directory' }`. URL строго `/<slug>/`.
- Звичайні сторінки (`/about/` тощо) мають пріоритет над динамічним маршрутом; slug міста не повинен збігатися з іншими сторінками.

### 3. Шаблонізація контенту
- Тексти шаблону — в Частині A (A14) зі змінними: `{city}`, `{inCity}`, `{genitive}`, `{region}`, `{brand}`, `{price}`.
- Хелпер `src/utils/template.ts`: `fill(str, city)` замінює змінні; невідома змінна = помилка збірки (щоб не потрапило `{city}` у HTML).
- Спільний каркас (hero, переваги, кроки, ціни, форма) — компоненти з A7, що приймають `city` як prop.
- Для міст використовується той самий набір блоків, що й на головній, **плюс** `LocalUniversities`, `OtherCities`, локальний FAQ.

### 4. Унікальність (правило 30–40%)
- На кожній сторінці міста ≥ **30–40%** тексту — унікальні локальні дані: ВНЗ міста, регіональна специфіка за напрямами, локальний FAQ, `intro`.
- **Агент не вигадує локальних фактів.** Якщо в A14 для міста немає даних, ставить `TODO`, лишає `localContentReady: false`.
- Для `localContentReady: false`: у `<head>` `<meta name="robots" content="noindex, follow">`, сторінку **не** додавати в sitemap, в `OtherCities` і футер. Для `true` — індексація, sitemap, перелінковка.
- Фільтр sitemap: `sitemap({ filter: (url) => !noindexUrls.includes(url) })` (список формується з `cities.ts`).

### 5. SEO кожної сторінки міста
- `<title>` і `<meta description>` — із шаблонів A14 зі змінними, унікальні для кожного міста; перевірити довжину (title ≤ 60, description ≤ 160). Довгі назви («Біла Церква») — скоротити шаблон, не обрізати слово.
- `<h1>` містить місто (`{inCity}`).
- Canonical — **сам на себе**: `https://<домен>/<slug>/`.
- OG-теги з урахуванням міста; `og:url` = canonical.
- JSON-LD: `ProfessionalService`/`Service` з `areaServed: { "@type": "City", "name": "<місто>" }` + `BreadcrumbList` (Головна → Місто). **Не вигадувати фізичну адресу в кожному місті.** Адреса лише якщо вона реальна й вказана в A2.
- `<html lang>` з A1.

### 6. Внутрішня перелінковка
- Компонент `OtherCities.astro` наприкінці кожної сторінки міста (і футер): посилання на **всі інші готові** міста. Текст анкора з A14 (напр. «Дипломні в {inCity}»), без перенасичення ключами.
- Хаб `/mista/`: список усіх готових міст з короткою підводкою; лінк на хаб у футері.
- З головної — посилання на хаб і/або блок міст.
- Усі лінки — звичайні `<a href>` (без JS), з `/` в кінці.

### 7. Форма
У `LeadForm` на сторінках міст — приховане поле `city` (slug міста) і, за потреби, `page_url`. Телефон і контакти — спільні (з A2); **не** підставляти різні номери «під місто».

### 8. Перевірка — `scripts/check-seo.mjs`
Після `npm run build` скрипт читає `dist/**/index.html` усіх міст і перевіряє:
- title, description, h1 — унікальні між містами;
- canonical == власний URL;
- у HTML немає нерозкритих `{...}`;
- noindex-сторінки відсутні в `sitemap-0.xml`;
- кількість внутрішніх лінків `OtherCities` = кількість готових міст − 1.
Падає з кодом 1 при будь-якій помилці; додати в `package.json` як `"check:seo": "node scripts/check-seo.mjs"`.

### 9. Чого не робити
- Не копіювати сторінку з заміною лише назви міста.
- Не вигадувати відгуки, адреси, телефони, ВНЗ чи факти для міст.
- Не робити сторінки міст без посилань на них з інших сторінок (orphan pages).
